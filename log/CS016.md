### Two seats the plan's text did not name, and why they are not design

Both were forced by an ANSWERED behaviour meeting a seat the plan named; neither
changes what the game does.

1. **The scan runs in the Dive's branch too.** Plan §3 seats `promptScan()`
   after the filters and before `updateSpawner()`, and N2 row 9's trigger is
   `state.dive.active` with rings laid. `update()` returns from the dive branch
   ABOVE that seat, and a dive ends in `resetDive()` on its last step, so at the
   named seat `dive.active` is never true — row 9 would never fire. The dive
   branch calls the same scan after `updateDive()`, with
   `WELLS[state.wellIndex]` (the dive's last step has already entered the next
   well). A step reaches exactly one of the two, so "one fire per step" holds.
2. **`promptStep()` sits ABOVE the dive branch**, not beside the scan (plan
   §3's wording): N4's answered behaviour is "a pause holds a prompt and a dive
   continues it", and beside the scan it would never run on a dive step.

### "saveTelemetry()'s four seats" — the plan's list, not the function's

`saveTelemetry()`'s real callers are `runEnded()`, `beforeChange`, `autoPause`
and `toggleTelemetry()` (capture turned off, off play). The plan and the prompt
name the four seats as the clear edge, `runEnded()`, `autoPause` and
`beforeChange` — the clear edge instead of the toggle. P1 built the prompt's
explicit list. The toggle is not a seat for the marks; the clear edge is,
because it is the one play step the pin (`test-cs015-p2.js:431`) exempts.
`savePrompts()` writes only when a mark is unsaved, so a session that has seen
everything writes the key never again.

### Calls inside the answers

- **One fire per step, in table order.** Two rows true on one step fire on
  consecutive steps; the scan returns the id and `Game`'s one wrapper,
  `scanPrompts()`, marks it through `Meta.promptSeen()`. A stubbed scan returns
  nothing and marks nothing.
- **"Stops reading the board once every row is seen"** is structural: the size
  test comes first, and an unseen row is the only path into `promptFires()`.
  Asserted with a Proxy that counts property reads (0 with all seen, >0 with one
  unseen). The loaded set holds KNOWN ids only, so the size test is honest.
- **Row 12's counter** is `Meta.unlocks()`, the count `sounded()` sounded since
  this profile was activated — reset beside the seen set in `loadPrompts()`, so
  a switch never hands one profile's unlock to another. An unlock at the run's
  end fires the row on the next run's first play step.
- **Rows 8–11 need no mode test**: each reads something only an Overdrive
  schedule releases (a token, a laid ring, a Warden, a Mimic); a bench key that
  puts one on a Classic board fires the row, as a bench Carrier does. Row 12
  (an unlock) fires in either mode.
- **The fade is in the colour**: `drawText()` sets its own `globalAlpha` for the
  glow's two passes, so a context alpha would be overwritten. `drawPrompt()`
  builds an `rgba()` from `C.PROMPT_COLOR` (parsed once) during the last
  `PROMPT_FADE` only — ⚠ one short string per frame for 0.5 s per prompt, which
  CS017's allocation measurement (F4) may want to see.
- **`promptReset()`** is `startGame()`'s one line; `Game.reset()` does not
  touch the queue (nothing asked it to, and every closed test starts a run).
- **Only `activateSettings()` gained a line** (`loadPrompts()`), so boot and a
  switch both reset-then-load; `hooks.resetSettings();` — a closed `mutate`
  string — is untouched.

### `test-cs016-p1.js` — what it proves and the mutation record

159 assertions. Staged: each of the twelve rows fires once on its own trigger
and is marked; 600 steps of every trigger plus a RESTART fire nothing; a reload
over the same store fires nothing it saw; a new profile starts empty and sees
the first line again; a switch back loads p0's marks; the unlock count resets
at a switch; a blocked store shows the first line in each of two sessions; the
key is declared, per profile, `{ seen }` at v1, removed with the profile; an
unknown id or junk loads as nothing; each of the four seats writes, a seat with
nothing unsaved does not, and the only play-step write is the clear edge's.
The queue: one fire per step in table order, FIFO, the head leaving on the step
its clock reaches `PROMPT_TIME` (241 aged steps — `1/60` summed 240 times is
under 4.0), a pause holding the clock, a dive running it, a death keeping the
queue and `startGame()` emptying it. The line: the head only, centred, at
`PROMPT_SIZE` and `PROMPT_COLOR`, the fade at half alpha mid-fade, drawn on play
and pause and on no other screen; drawn after the rungs and before the token,
the enemy, the craft and the HUD. The band clears the throat zone on all
sixteen wells, is under every rim and the grounded craft, and clears all six
HUD rectangles at their widest in both mirrors. The scan spends no draw, reads
no clock, writes no `state`, and reads nothing once all is seen.

**Played:** Classic from Start Depth 9, a fire-holding mover, 9,600 half-frames
through `Game.frame()`: the working build fired `rotate, openWell, thorn,
carrier, drifter, unlock` and wrote `onboarding` twice, both at clear edges;
the twin with `promptScan` and `promptStep` stubbed hashes identically on every
frame and fired nothing.

**Mutations (each string asserted in the build exactly once first):**
- `if (seen.has(row.id)) continue;` out → the first line fires again (red).
- `loadPrompts();` out of `activateSettings()` → a new profile inherits the old
  one's marks (red).
- a `Meta.savePrompts()` beside the mark (the rejected trigger-step write) → a
  play-step `onboarding` write (red) — which is exactly V3's finding.

### A fixture trap found on the way

`beforeChange`'s legitimate write look like a play-step write to a `Store.set`
spy. In the game a switch is always a menu action; the test stages it on
`profilePage`. Recorded in `STATUS.md`'s test hazards.
