### Two seats the plan's text did not name, and why they are not design

Both were forced by an ANSWERED behaviour meeting a seat the plan named; neither
changes what the game does.

1. **The scan runs in the Dive's branch too.** Plan §3 seats `promptScan()`
   after the filters and before `updateSpawner()`, and N2 row 9's trigger is
   `state.dive.active` with rings laid. `update()` returns from the dive branch
   ABOVE that seat, and a dive ends in `resetDive()` on its last step, so at the
   named seat `dive.active` is never true — row 9 would never fire. The dive
   branch calls the same scan after `updateDive()`, with
   `WELLS[state.wellIndex]` (the dive's last step has already entered the next
   well). A step reaches exactly one of the two, so "one fire per step" holds.
2. **`promptStep()` sits ABOVE the dive branch**, not beside the scan (plan
   §3's wording): N4's answered behaviour is "a pause holds a prompt and a dive
   continues it", and beside the scan it would never run on a dive step.

### "saveTelemetry()'s four seats" — the plan's list, not the function's

`saveTelemetry()`'s real callers are `runEnded()`, `beforeChange`, `autoPause`
and `toggleTelemetry()` (capture turned off, off play). The plan and the prompt
name the four seats as the clear edge, `runEnded()`, `autoPause` and
`beforeChange` — the clear edge instead of the toggle. P1 built the prompt's
explicit list. The toggle is not a seat for the marks; the clear edge is,
because it is the one play step the pin (`test-cs015-p2.js:431`) exempts.
`savePrompts()` writes only when a mark is unsaved, so a session that has seen
everything writes the key never again.

### ⛔ A defect the plan predicted away, MEASURED red and fixed

N9 predicted "the title's entry step latches whatever is held, so the ending
press confirms no row." **False as written for an ending inside a step.** The
struct-reading ending (and a named action, both inside `update()` before its
second `syncScreen()`) makes THIS step the title's entry step, and
`quitToTitle()` re-mints `state` from `newState()` — `state.input` included. The
entry step latched a fresh at-rest struct, and the Fire that ended the demo
was a rising edge on the next step: PLAY confirmed, screen `mode` (MEASURED, the
test's first run). A normal QUIT TO TITLE never meets this because it happens
in a menu step and the entry step is the NEXT update, which samples first.
Fix: `endAttract()` keeps the step's struct object across `quitToTitle()`
(`state.input = held`). `frame()`'s seat needs none of it (the next step
samples before its entry step) and calls `quitToTitle()` directly. The
mutation is in the test.
