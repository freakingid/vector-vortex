## P1 — the rim fix: (A) + (B) + ε, and 100 % killable at the rim

Built from `PLANNED-FEATURES-CS008.md` §2, on Paul's R1/R2 calls. Nothing
designed here.

**What shipped.** (A), ordering A1: `updateShots()` ages and filters, then
fires, and the `SHOT_MAX` check reads the post-retirement length. (B): the
Vaulter, Carrier, Drifter and Surger climbs clamp at `1 - C.RIM_CONTACT_DEPTH`,
written as that expression in each (never `this.killDepth`, which the Surger
zeroes), and `Vaulter.atRim()` reads the same expression. The `WeaverBolt` is
untouched. (ε): `C.HIT_DEPTH_EPS` 1e-9, in `collideShots()`'s band test only.

**Why four samples now.** A shot moves `DT / SHOT_TIME` ≈ 0.03205 per step, so a
fired shot is tested at 1.000, 0.968, 0.936 and 0.904. All four are within
`HIT_DEPTH_TOL` of 0.95 — but the first only with ε, since `|1 - 0.95|` is
0.050000000000000044. Four consecutive samples against a four-step cadence is
every phase. Without ε, or without (A), it is three of four, which is exactly the
18/24 the mutations below produce.

Because the hash matched to the digit before any test was edited, the code is
behaviourally §2's; both re-records carry one cause at the assertion. The golden

**Closed-file repairs, in place (§1.5).** Park-depth rewrites in `cs003-p1`,
`cs004-p2`, `cs005-p2`, `cs005-p3` — including tightening each file's `> 1`
overshoot bound to the park depth (in `cs005-p3` that is the `boundFail` range,
which was the climber's overshoot bound) — and `cs003-p5`'s `sawRim`. The two
vacuous soaks (`cs004-p5`, `cs005-p5`) now exclude the bolt. `cs007-p3`'s level-22
window doubled. ⚠ Not tightened: `cs003-p5`'s soak-wide `depthOut` range `[0, 1]`.
It is a legality bound across a live board, not a claim about where a climb
stops, and §1.5 did not list it.

**Test design.** `test-cs008-p1.js` follows the planning probe's scenario
shapes (`p-rim.js` in the planning session's temp dir, read for fixture parity
only): S1 Vaulter at the park depth one lane over, S2 a Vaulter climbing from
0.5, S4 a Drifter two lanes over, 0..23 ticks of pre-fire each. It runs on the
Ring (Skimmer at lane 0) and on the Vee (Skimmer at lane 5, clear of both walls).
It also asserts A1 directly: a fire-tick shot is at depth 1, and with eight shots
in flight a retiring one frees its slot for the same step's fire, which A2 would
refuse.

## P1b — the crossing fix: the rim sweep

Built from `PLANNED-FEATURES-CS008.md` §2b, on Paul's K1–K4 calls. Nothing
designed here.

**What shipped.** §1.16's four lines in `collideSkimmer()`, after the lane match
and before `killSkimmer()`: with `state.input.fire` held and
`e.depth >= 1 - C.RIM_CONTACT_DEPTH`, ask `e.onShot(null)`; if it died, count the
kill and `continue`. No change to `updateShots()`, the cooldown, `SHOT_MAX`,
`HIT_LANE_TOL` or the contact geometry. The file header, `collideSkimmer()`'s
header (the four decisions, and §1.16's C10/C13 numbers as the reason it is
contact-side) and the "No scoring" note were corrected in place.

**Predicted vs measured.** The code went in first, then the suite ran before any
test was touched.

|---|---|---|
| Suite under the sweep alone | 5 failures: three soaks' game-over stop, `cs007-p4` deaths, the hash | **the same 5, same messages** — no new cause |
| Hash, sweep alone | 4203989832 | **4203989832** |
| Hash, fixtures alone (sweep reverted) | 2859072280 | **2859072280** |
| Hash, both | 1229033515 | **1229033515** (35/36 green before the re-record) |

| Guards (`GOLDEN_LANES`, draws-per-spawn, `cs007-p2`, `cs008-p1`) | green, no edit | **green, no edit** |

Because the three hash values matched to the digit, the code behaves exactly as
§2b's and the fixtures are §1.16's. The soak counts behind the repair (L7 and L23
each 2 deaths / 1 game over / 1 respawn) were not re-instrumented: an identical
hash is an identical run.

**Closed-file repairs, in place.** `st.lives = 1` after the first `armMixed()`
in `hashRun()` of `cs004-p5`, `cs005-p5` and `cs006-p5`. `cs007-p4`'s
`CAPTURE_TICKS` went from 6,000 to 7,300. Each comment says it restores a
precondition, and why only the first run: under the sweep the fire-holding
scripted player dies too rarely.

**Test design.** `test-cs008-p1b.js` uses §1.16's stagings. For fixture parity
only, I read the planning session's throwaway `cross-probe.js` in its temp dir;
the plan document is what the test follows.
- **Setup.** Each row gets 40 + p ticks of pre-fire (p = 0..23). The enemy is
  placed two lanes out and the Skimmer crosses to four out, then waits 20 ticks.
  `killed` means no `blocksClear` enemy is alive; `died` means lives dropped;
  anything else fails.
- **Non-vacuity.** The rack is `SHOT_MAX` at placement on every fire row, and
  **empty** on N1, which shows fire really is not held. C4 stands on exactly
  6.5 in all 24 phases. C7 and C8 count 3 kills per phase. C13 checks both
  placed objects are `dead`.
- **Measured on the fixed build.** Every row matches the plan's sweep column.

**Mutation record.** Each mutation was applied to `src/09-collision.js`, the
build rebuilt, `test-cs008-p1b.js` run, and the file reverted. The final
rebuild and suite are green.
