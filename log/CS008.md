## P1 — the rim fix: (A) + (B) + ε, and 100 % killable at the rim

Built from `PLANNED-FEATURES-CS008.md` §2, on Paul's R1/R2 calls. Nothing
designed here.

**What shipped.** (A), ordering A1: `updateShots()` ages and filters, then
fires, and the `SHOT_MAX` check reads the post-retirement length. (B): the
Vaulter, Carrier, Drifter and Surger climbs clamp at `1 - C.RIM_CONTACT_DEPTH`,
written as that expression in each (never `this.killDepth`, which the Surger
zeroes), and `Vaulter.atRim()` reads the same expression. The `WeaverBolt` is
untouched. (ε): `C.HIT_DEPTH_EPS` 1e-9, in `collideShots()`'s band test only.

**Why four samples now.** A shot moves `DT / SHOT_TIME` ≈ 0.03205 per step, so a
fired shot is tested at 1.000, 0.968, 0.936 and 0.904. All four are within
`HIT_DEPTH_TOL` of 0.95 — but the first only with ε, since `|1 - 0.95|` is
0.050000000000000044. Four consecutive samples against a four-step cadence is
every phase. Without ε, or without (A), it is three of four, which is exactly the
18/24 the mutations below produce.

Because the hash matched to the digit before any test was edited, the code is

**Closed-file repairs, in place (§1.5).** Park-depth rewrites in `cs003-p1`,

## P2 — scoring and extra lives

**Built as plan §3.** `addScore(n)` and `clearBonuses(state)` live in
`12-scoring.js`. `points()` is the fourth contract method. The three kill sites
award on the false → true transition. The clear edge calls `clearBonuses()`
before `startDive()`. `state` gains `score`, `nextLife` and `diedThisWell`.
`score` left `C.TELEMETRY_PLACEHOLDER`. One judgment call inside the plan: the
bonuses are a function in `12-scoring.js` rather than three lines in
`23-main.js`, so scoring stays in its module and P3's Start Depth bonus has one
place to go. The dive termination gained a comment and no code.

**Predicted vs measured.** The code went in first, then the suite ran before
any test was touched.

The three new causes went into `STATUS.md` before any edit:
1. `_harness.js` exporting `addScore` turned `cs003-p3:88` and `cs003-p4:125`
   (*"no addScore exists yet"*) red.
2. `cs004-p1:77` pins the prototype at three signatures.
3. `cs007-p4:149,153` read `C.TELEMETRY_PLACEHOLDER.score`.

§1.8's emulation exported nothing, added no method and deleted no key, so it
could not see them. All were rewritten in place to the replacement claim. The
two "still unread" source-text assertions became "exactly one reader, and it
is that class's `points()`". For that to hold, the Drifter's comment avoids
naming the constant.

**Test design (`test-cs008-p2.js`, 125 assertions).**
- **Staged rows.** Expected values are GDD §7's literals, never `C.PTS_*`.
  - Drifter boundaries run through the Purge, which moves nothing: exactly ⅓
    pays 500, and ⅓ − 1e-9 pays 250.
  - A Thorn at 0.2 takes three chips. 0.24 would take four, because
    0.24 − 3 × 0.08 = 2.8e-17.
  - A child born and killed in one pass is staged with two shots. A sweep
    cannot do it: the safe-spawn rule lowers a child born in the Skimmer's
    lane. Measured when the first staging came back 100 against 250.
- **Item 8.** Eight played boards: levels 1, 13, 17 and 23, held or pulsed
  fire, three Purge cadences, 15,000 ticks each.
  - Every step's delta is priced off the board: each entity that is dead after
    the step, the step's pushes included; each Thorn's chips; and each clear's
    bonuses, with the test tracking deaths per well itself.
  - A chip is decoded against the length at the step's start, raised to the tip
    of a Weaver that was climbing and grew it. Every live Thorn decodes to
    whole chips within 1e-9.
  - Measured over 120,000 steps: 0 mismatches, 403 chips, 139 Purge kills and
    59 clears. The no-death bonus was paid 37 times and withheld 22. The unspent
    Purge was paid 21 times. There were 8 milestone steps, 118 deaths, and 2
    dive deaths after a paid no-death.
- **No draw.** `_harness.js` gained `buildGame({ stub })`, which rebinds a named
  top-level function to a no-op after evaluation.
  - Stubbing only the effect, with a `score` setter, would still run a draw
    inside `addScore()` in both builds.
  - The window ends at the first game over in either build: 14,211 ticks, 402
    draws, score 43,485, with a life awarded inside the window. Per-tick draws
    and boards are identical.
