### The tool — `tools/perf-probe.js`

Rebuilt from the planning session's throwaway probes (its scratchpad survived:
`cdp.js`, `browser-probe.js`, `fps-probe.js`), as one Node file with no npm
dependency: Chromium from `CHROME_BIN` or Playwright's cache (else exit 2 with
the reason — both paths run: `HOME=/nonexistent` and `CHROME_BIN=/nope`), the
DevTools protocol over Node 24's own `WebSocket`, a throwaway `--user-data-dir`
per launch so no stored profile leaks between runs. ~27 s a run.

Four things changed from the throwaway, each MEASURED first:

- **Bytes per `draw()` are the JIT's as much as the source's.** The same
  board read 8,196 B after 300 warm draws, 7,738 after 1,000 and 7,076 after
  5,000: TurboFan inlines `projectPoly()` into `drawWell()` (its bytes move
  names) and unboxes some doubles. So the tool reports TWO readings per board
  — after 300 draws (plan §1.3's method) and after 5,000 more ("steady").
- **Each board gets its own page.** Measured in one page, the second board's
  first reading inherits the first's warm-up: the budget board read 7,363 B
  after the empty board and 8,196 before it. This also explains the plan's
  empty-board figure: its 1,819 B was measured after three other boards, and
  matches this tool's STEADY reading (1,856), not its first (3,017).
- **The frame row is S2's board exactly, and it is a death freeze.** The
  fragments exist only on a dead craft, and a dead craft's frames run no step,
  so the row times `draw()` + raster with the freeze held open by a rAF hook
  (`Game.hitStop` only raises). A live-loop row that re-staged whenever the
  board thinned re-staged on nearly every step (240 in 4 s) — it measured the
  staging — so the step's script cost is timed apart instead: 10 stagings × 12
  steps, the staging untimed (one staging stepped 120 times thins to 9
  enemies and 0 shots).
- ⚠ **One boot in five lost the first Space** (title → title → mode → depth),
  pressed before the title had run live steps. The probe now waits for 30
  ticks, waits for each screen change, retries a press once and COUNTS it
  (`boot.retries`; 0 in the five runs after).

### The four fixes — V4's edits, with two choices recorded

`drawShot()` hands `drawPoly` one module `_shotPair`; `drawText()`'s font from
`textFont(size)`, a per-size cache; `drawPrompt()`'s fade from

- **`C.PROMPT_FADE_STEPS` is new** (the plan said "per 1/100"): `CLAUDE.md`

- **The string keeps CS016's `toFixed(3)`**, so a cached colour reads exactly
  as the shipped one at every step (V4 used `toFixed(2)`); it stays correct for
  any step count up to 1,000.
