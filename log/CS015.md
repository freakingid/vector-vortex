### A12's collision, resolved by `createScores`' seam — and what `defs` is

⛔ The config invariant ("every tunable in `C`") and the boundary contract ("a kit
module names no `C`") point in opposite directions over a table whose tier
thresholds are tunables. §1.9 MEASURED the shipped resolution: `createScores`
takes `perMode` from the config as an **option**, so the number is where a tuning
pass finds it and the module still reads nothing. `createAchievements` takes the
whole definition table the same way.

**Plan §7 asks for TWO tables kept apart; the prompt asks for FOUR options.** Both
hold: the definition table is one option whose value carries two arrays —

```js
ACHIEVEMENTS: { perWeek: 5, lifetime: [ … ], weekly: [ … ] }
```

`lifetime` is what exists and what each row reads; `weekly` is the pool that
rotates. Neither array names the other's numbers, the rotation reads
`weekly.length` and `perWeek` and nothing else, and nothing derives a pool index
from a lifetime row's tier — which is the whole of §7. The alternative, a fifth
option `pool`, was rejected because the prompt and plan §3 and §8 all name
exactly `{ defs, load, save, now }`, and a build phase invents no interface the
plan did not price.

### The row shape, and why an untiered row is a second key rather than a flag

A row is `{ id, mode, fact }` plus **exactly one of** `tiers: [t1, t2, t3]` or
`at: n`. A11 makes the payload's `tier` the 1-based index reached and **0 for an
untiered row**, so the two kinds are genuinely different answers and not one
answer with a null in it. Making them two keys means the factory can REFUSE a
row that carries both or neither, at construction, with a named message —
`createScores`' shape — rather than at evaluation, which is where A12-B's
rejected variant would have failed.

`mode` is `"classic"`, `"overdrive"` or `null` (A5): the tag is a property of the
achievement, so a third mode is a table edit and `C.MODE_FLAGS` gains nothing.

### The placeholder ids, and why they are prefixed

⛔ An id that reaches a player's store is save data from that moment on. P3
replaces the rows' contents whole, so P1's rows must be ids **nothing will ever
store under**. Two guards, not one: every placeholder id starts `_`, which no
shipped row in §9 does, **and** P1 builds no evaluation seat at all, so the
shipped build has no caller of `evaluate()` and cannot write the key. A stored
placeholder id would in any case be dropped on read — unknown ids are dropped,
which is A6's known-value-else-default rule doing its job.

### The ISO week, MEASURED

The function is `isoWeekKey(ms)`: the UTC calendar day, shifted to that ISO
week's Thursday, whose UTC year is the ISO year; the week number is counted from
the Monday of the week holding 4 January. Its constants — a day in ms, 7 days, the
3-day shift to Thursday, 4 January, the 53-week ordinal base — are **ISO-8601's
definition, not tunables**, and they stay local: a kit module may not read the
game's config, and the config invariant is about knobs a tuning pass turns.
Recorded here because it is the one place in this phase where the two rules were
weighed and the answer was "neither applies".

MEASURED, all eight cases green before the module was written (a scratch probe,
then re-asserted off the build in `test-cs015-p1.js`):

| Instant (UTC) | Key | Why it is a boundary |
|---|---|---|
| 2020-01-01 | `2020-W01` | Wednesday; week 1 straddles the year |
| 2021-01-01 | `2020-W53` | ⛔ the 53-week year naive code gets wrong |
| 2025-12-29 | `2026-W01` | Monday of the NEXT ISO year, in December |
| 2026-01-01 | `2026-W01` | Thursday; the anchor day |
| 2027-01-03 | `2026-W53` | ⛔ Sunday; the last day of the previous ISO year |
| 2027-01-04 | `2027-W01` | the Monday after it — the roll |
| 2026-09-20 23:30 | `2026-W38` | ⛔ Sunday late: UTC reads the EARLIER week |
| 2026-09-21 00:00 | `2026-W39` | the roll, 30 minutes later |

The Sunday 23:30 pair is the one the UTC rule exists for: any local reading east
of UTC already says W39 at that instant, so two devices would disagree about
which five are live.

### The rotation, MEASURED

A stride walk, pure integer arithmetic on the key: `ord = year * 53 + week`,
`start = ord % n`, `stride = 1 + (ord / n | 0) % (n - 1)`, then `perWeek` picks at
`(start + i * stride) % n`, stepping to the next free index on a collision.
⛔ It spends no draw, calls no clock beyond the key it is given, and reads no
board — which is why a dive, a spawn or a soak's hash cannot move under it.

MEASURED over a pool of 20 and 104 weeks (2026-W01 … 2027-W52): **68 distinct
sets, all 20 entries touched, 24–27 appearances each**, and one key returns the
same five on every call. Plan §1.6's probe measured the same walk over a pool of
29 and reported 98 distinct sets over 104 weeks; the drop to 68 is the smaller
pool, not a different function — with `n` 20 the start cycles every 20 weeks and
the stride every 400.

## P2 — the facts, the seats and the gate (2026-09-20)

### The thirteen counters, and where each one had to go

A2-A's answer is one flat `facts` object built at the seat, from `state` plus
new `tally` fields. §9's table needs eleven new fields; the shipped count is
**thirteen**, and the two extra are the tiered rows' arithmetic rather than a
new idea. `purge_saver` is ⚠ tiered 5 / 25 / 100 and `open_well` is `at: 1`;
§9's *Reads* column gives each as a READING at the clear edge (`purgeUses === 0`,
`WELLS[i].closed`). A reading is a boolean and cannot reach a tier of 25, so
each is COUNTED where it is read — `purgeSavedClears` and `openWellsCleared`,
beside `tally.wellsCleared` — and the row's threshold is then arithmetic on a
run's own counter like every other row. ⛔ No row's MEANING moved.

Two of the thirteen are BITMASKS rather than counts, and that is the same
argument: `all_wells` is "sixteen DISTINCT wells in one run" and `token_set`
"all five KINDS", and distinctness needs a memory. `wellsSeenMask` and
`tokenKindsMask` are written where the event happens (`enterWell()`, the token
pickup) and Meta hands the FACT over as a bit count — `wellsSeen`, `tokenKinds`.

⛔ **Every counter sits beside the counter or the event already at its place**,
and nothing in the simulation reads one (02-state.js's own rule, which is what
keeps the determinism hash identical).

### The `brood`, and why a Carrier's split needed one

`carrier_split` is "destroy a Carrier and BOTH its children in one well" — the
one row §9 has no measurement for. Nothing in the build linked a child to its
parent: `Carrier.onShot()` spawns two through `spawnEnemy()` and forgets them.
So the split now hands both children ONE shared `{ left: 2 }` object as
`e.brood`, and `tallyKill()` counts the split on the second of them destroyed.
⛔ **Only when BOTH were spawned**: a child refused at `C.ENEMY_CAP` leaves no
pair to finish, and the row is about a pair. ⛔ It is not a contract field and
nothing reads it: a Purged Carrier never splits (⚠ SETTLED, by omission), so it
never mints one.

### `tallyKill()`, and the five kill lines that are NOT edited

Two counters depend on WHAT died: `mimicKills` and `carrierSplits`. Both are
decided at the kill lines — and ⛔ **the five kill lines are pinned by closed
tests** (`test-cs012-p4.js`'s six `COMBO_OUT` strings, `test-cs014-p1.js`'s
count of four and its fifth). So `tallyKill(state, e)` is called on its OWN
LINE above each of the four lines a Mimic or a child can reach, under the same
condition the kill line reads, and the kill lines' text is untouched. The jump
strike needs no call — only an `aloft` entity dies there, which is neither —
and takes `state.tally.jumpKills++` beside its `tally.kills++`. `instanceof
Mimic`, never a kind string: a `MimicShot` is not a Mimic. MEASURED: the closed
pins are green with no edit, exactly as plan §11 predicted under A2-A and A9-A.

### The two seats, the gate, and the order that hides a bug

A3-A's seats are the clear edge (`Meta.clearEdge()`, after the bonuses and
`noteCleared()`) and `Meta.runEnded()`. ⛔ **The run-end seat reads `ok`, the
local**: `runEnded()` nulls `run` BEFORE it does anything, so `eligible()` is
false inside it and a seat written the obvious way would make every run
ineligible while nothing else said so. That mutation is in the test and is red:
`eligible()` in place of `ok` evaluates NO run's end.

A4-A: `Meta.eligible()` gains a THIRD caller and no change — the `GATE` string

### ⛔ A FINDING: a closed soak was repaired, and the cause is the CLOCK

⛔ Plan §11 predicts NO closed-file edit at P2. One was needed, and it is not
one the table names: **`test-cs013-p5.js`'s driver**, the eleventh soak.

⛔ **What the next phase must know**: every closed soak that fakes `Date.now`

### ⛔ A row is one fact `>=` one threshold, so two shapes are decided game-side

The weekly pool needed three shapes the row form cannot state, and all three are
built in `facts()` (`22-meta.js`) with ⛔ **no new `tally` field and no module
change**:

- **A per-well window is the DELTA SINCE THE LAST CLEAR EDGE**, kept beside
  `run` in Meta's closure and reset by `runStarted()`, because `tally` is
  monotonic within a run and the edge fires once per well. The streak moves
  before the facts are built and the window closes after they are read, so a
  clear sits inside its OWN window; ⛔ both move above the eligibility gate, or a
